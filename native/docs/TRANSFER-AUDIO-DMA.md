# Metalio 音乐上传慢与播放读取失败

2026-10-29，安装的主应用为保留36相黑到黑校正的 `0.0.1-v1-beta`。
本次通过不复位、不发送数据的 COM5 监听采集现场。设备 USB 标识匹配 Metalio，
没有重启、取消上传、重新上传或改写设备文件。

## 上传速率与证据边界

用户使用手机与设备连接同一路由器，约9.5MB音乐上传四五分钟。
现场记录的请求大小为9,453,466字节，处理耗时231,761ms，日志速率40KB/s。
旧日志无论成功或失败都用请求的声明大小计算速率，因此这条日志不能单独证明
完整接收、落盘或播放文件完整；本轮尚未取得上传源文件与SD文件的哈希对照。

当前 STA 在 `thingsos_net/network.c` 中明确限定802.11b/g。
802.11g链路最高54Mbps，即6.75MB/s原始比特率换算，不是HTTP写SD的可用吞吐。
上传已有16KiB接收块、32KiB stdio缓冲和临时关闭modem sleep。
TCP接收窗口为5760字节，每轮接收写入后延时1ms；上传进度界面至多每2秒刷新，
显示期间持有与SD写入共用的I/O锁。因此链路、接收窗口、锁等待和SD写入都可能
影响吞吐，需要分别计时，不能将40KB/s全部归因于802.11g或SD卡。

录到的上传处理日志之后出现休眠断开WiFi、唤醒后的连接重试和未取得地址。
这些事件发生在上传处理结束之后，不能用它们证明前面232秒一直在断连。

## 播放错误已重现的直接原因

用户再次播放同一首歌并确认错误重现，串口记录：

```text
691739 ms  Started play ... buffer=524288
693384 ms  sdmmc_cmd: allocate_dma_buf: not enough mem, err=0x101
693385 ms  diskio_sdmmc: sdmmc_read_blocks failed (0x101)
693385 ms  ThingsOS_audio: State=7 error=5 message=音频读取失败
```

首次预读后可播放约1.65秒；后续SD读取临时DMA缓冲申请失败触发停止。
这次直接失败点是SD DMA内存申请，不是MP3解码报错，不能据此断言SD卡已损坏。

本地ESP-IDF v6.1的 `sdmmc_cmd.c` 在目标不满足DMA要求时使用临时缓冲，
默认主机批量为16扇区。申请失败会逐次减半，直到不足一个扇区才报本次错误。
因此不是简单把一次大读拆小就能保证解决：现场连单扇区DMA临时缓冲也未申请到。
该SDK已经提供 `sdmmc_host_t.dma_aligned_buffer` 复用接口。

## 修复候选

Metalio BSP在挂载SD前预留64字节对齐的DMA缓冲，优先8192字节，内存不足时按
4096/2048/1024/512字节退让，最小扇区也不可分配则安全拒绝挂载。
SD主机使用该缓冲及对应批量，后续读写无需再申请该临时搬运缓冲。
缓冲保留到板级生命周期结束；FAT重挂载及独占的USB raw-card阶段复用同一块。
其他SD请求仍遵循既有FAT/USB所有权与I/O互斥，频率、位宽、引脚保持原值。

上传增加成功状态、实际接收字节数、接收调用次数，以及接收/等锁/写入/同步耗时。
原有上传速率日志改用实际接收字节数，失败不再按完整声明大小报告吞吐。
未改变WiFi协议、TCP窗口、字形或已验收的36相阅读校正。

新增主机回归覆盖8KiB至512B退让、初始化后的DMA堆耗尽、32轮重挂载/raw复用、
无后续分配，以及低于一个扇区时安全失败。主机回归35/35通过。
主应用及救援构建均通过，主镜像校验和与摘要有效，主应用版本保持 `0.0.1-v1-beta`。
