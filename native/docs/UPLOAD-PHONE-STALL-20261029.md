# 20%刷新版之后的手机上传停滞

用户反馈：手机网页进度超过一半后停住，文字为“正在准备上传文件”，
随后按诊断要求取消了该次上传。当前安装的是20%刷新候选，
ELF `76791622c74ad17b47b560b556002c53cc93b6289b1d8cdf5d6b6592f4007782`。

## 本次实际观察

- 已保存的串口日志没有任何 `Upload ... bytes in ...` 或 `Upload timing` 记录，
  也没有进入文件写入阶段通常出现的 `wifi:Set ps type: 0` 记录。
- 约293.9秒有三个 `httpd_sock_err: error in recv : 104`，
  日志没有请求标识，不能把它们直接归到此次上传，更不能据此认定根因。
- 手机确认取消前的一次HTTP状态读取成功，设备返回 `healthy=true`、
  `busy=false`、`service=true`、`sd=true`、`audio.state=0`。
  内部空闲96,971字节，历史最小42,044字节；DMA空闲64,211字节。
  该时点没有有效上传占用，不能把网页停住当成设备仍在接收文件。
- 本次没有完整成功上传样本，不能与此前301.489秒做吞吐比较。

## 已确认的网页缺陷及源码修正

1. 新上传开始时没有清零旧进度。现于准备与每次发送开始时清零，
   避免旧的半程进度被误读为本次进展。
2. 普通文件发送时没有更新“准备上传”文字。现区分准备、手机发送百分比、
   手机已发送但仍等待设备保存结果；只有成功HTTP响应才表示上传成功。
3. 原流程先尝试完整文件POST，收到409后才显示同名文件选择。
   现对当前目录列表里已知的同名目标（不区分大小写）先弹选择，
   选择保留两份/替换后直接携带相应请求头发送；取消不发送文件。
   服务端409回退仍保留，用于列表过期或目标尚未列出的情况。
4. 增加服务端上传请求入口及“读取正文前遇到同名”的日志，
   弥补只有写入阶段结束统计、看不到早期返回的诊断缺口。

这些修正处理已确认的可见性及同名流程缺口；尚未实机证明它们就是
本次停滞的原因。SDK在早期返回后会尝试清理未消费正文，当前purge缓冲32字节；
这是需要进一步对照的线索，不能由源码单独认定手机发生了该路径。
MP3在 `thingsos_prepare_image()` 中直接返回原文件，不做图片转换。
