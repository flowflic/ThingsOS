## 发现并修正的具体时序缺陷

原驱动只等待 LCD/DMA 完成。CKV 使用独立 RMT 发送，启动时安排 `display_lines + 5` 个行脉冲；LCD 结束时既没有停止 CKV，下一相重新设置 loop counter/read pointer 时也没有先停止旧发送。调整像素钟还会直接改写 CKV 波形内存。

因此，LCD 返回完成并不保证 CKV 的尾脉冲已经结束。局部加载动画的前缀多为保持行，准备下一相更快，会增大上一批仍活动时重新配置 RMT 的机会。这是从源码推导的竞态机制，并非对旧现场实测到的脉冲记录。

只读对照同板参考 `references/metalio-e-ink4-plus/main/boards/metalio-e-ink4-plus/display/output_lcd/lcd_driver.c` 的 `start_ckv_cycles()`，其顺序明确为先 `rmt_ll_tx_stop()`，再配置有限循环、复位读指针、启动。本次使用现有兼容层与 SDK LL API 独立实现停止/重启顺序，参考仓库未修改。

第三候选的处理：

1. LCD 帧结束和超时/中止时同步停止 CKV；重配有限循环前、改写 CKV 波形前均先停止发送。
2. 用 PCNT 从 CKV 实际 GPIO40 输入回读上升沿，不只看“已调用 RMT start”。每个完成相位必须观测到 688 至 693 个脉冲；读取失败、缺脉冲或多脉冲会返回扫描错误，进入现有完整目标重建和安全恢复路径。PCNT 仅增加输入采样，不改变输出路由或行高低电平时长。
3. 接入 ESP32-S31 的 `LCD_LL_EVENT_UNDERRUN`，在硬件欠载时终止当前相位并传播错误；不再只依赖软件行队列和 DMA EOF。

没有调整面板波形、VCOM EEPROM、充电策略或版本号，也没有发布或提交。原有 SDK RGB DMA 策略保留，未重新启用首候选中未通过实机启动验证的 owner/writeback 改动。

## 后续用户复测：条纹/冻结未再出现，加载切换黑闪

用户随后明确反馈：复测未再出现横条纹和卡死，但开始加载新章节、或加载完成时会短暂闪黑。该反馈构成本轮开书/章节加载场景的有限实屏验收，不能扩大为所有书籍和长期稳定性结论；此前 600 秒静置日志的边界保持不变。

黑闪的代码触发链已定位：

- 首次显示加载窗口时 `online.painted=false`，主循环调用 `online_modal_present_frame(false)`，进入 `online_modal_present_full()`。该函数无条件调用 `thingsos_board_full_refresh()`，再提交整屏加载目标。
- 章节就绪、窗口已显示时，`online_poll()` 设置 `app.force_refresh=true` 和 `online.cleanup=true`；主循环同样再次调用完整加载呈现函数。因此开始和结束加载各有一次主动整屏清理。
- 板层将 `full_refresh` 变为 `clean=true`，调用 `epd_hl_update_screen_full(...MODE_GC16...)`，使用完整 GC16 的黑白归一化过程。该路径不依赖欠载或其他错误，正常请求成功也会发生短暂整屏变黑。

这是此前为重建加载窗口前后光学基线添加的刷新策略，与 CKV 停止/重启修复分属不同层。用户本轮要求定位原因，因此本轮未改变已安装代码或刷新策略。后续若优化，应将正常进入/退出加载的呈现与真正错误恢复的整屏物理清理分开，同时保留 CKV 顺序及硬件脉冲检查；低闪方案仍需检查灰色遮罩和卡片残影。
