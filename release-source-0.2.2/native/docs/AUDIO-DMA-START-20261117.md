# 音频硬件启动失败与内部 DMA 资源

## 实机证据

用户在已安装的低闪阅读菜单候选上报告播放提示“音频硬件启动失败”。开启不复位的串口采集后，用户确认扬声器复现，并说明此前蓝牙耳机同样失败。证据：`build/audio-start-failure-20261117/live.log`。

日志在 683602 ms 记录 `i2s_alloc_dma_desc(720): allocate DMA buffer failed`，随后标准 I2S 初始化失败；音频服务返回 `error=257`（`ESP_ERR_NO_MEM`）。紧随其后的“channel has not been enabled yet”来自旧关闭函数对初始化失败的通道调用 disable。这些记录确认了 DMA 缓冲分配失败路径，但没有记录当时 DMA 总空闲/最大块，不能据此区分碎片化、总量不足或断言内存泄漏。采集结束已关闭串口。

## 当前 SDK 的内存要求

DMA 是传输方式，PSRAM 是存储介质。本机 ESP-IDF v6.1 的 `esp_driver_i2s/i2s_private.h` 将 `I2S_DMA_ALLOC_CAPS` 定义为 `INTERNAL | DMA | 8BIT`；`i2s_common.c` 通过该能力组合分配 DMA 数据缓冲及描述符。因此本驱动不能直接用 PSRAM 替代音频硬件缓冲。

现有音频服务已经把 512 KiB 文件预读、MP3 解码状态/工作区、PCM 解码与转换缓冲放在 PSRAM；内部 16 KiB 音频任务栈保留，以避免 NVS/Flash 缓存关闭窗口中的外部栈风险。本次不修改 SDK、不迁移硬件 DMA 缓冲到 PSRAM，也不缩减未经实际栈证据验证的任务栈。

## 修复候选

I2S 采用有界分配策略，保持 16 kHz、立体声 32 位插槽、从机时钟、引脚和正常配置不变：

| 顺序 | 缓冲配置 | PCM 数据容量 | 时间覆盖 | 目的 |
| --- | --- | --- | --- | --- |
| 1 | 6 × 256 帧 | 12 KiB | 96 ms | 原正常配置 |
| 2 | 12 × 128 帧 | 12 KiB | 96 ms | 减小单块申请，处理碎片化；描述符开销会增加 |
| 3 | 6 × 128 帧 | 6 KiB | 48 ms | 降低总内部 DMA 占用 |

仅 `ESP_ERR_NO_MEM` 触发下一配置；参数、通道冲突或其他错误原样返回。每次失败先删除通道并释放 SDK 部分分配，不重叠保留多套缓冲。记录申请阶段、配置、DMA 空闲总量及最大块。仅成功启用的通道才调用 disable，去除初始化失败时的无效停用错误。仍然不足时会保留明确失败，不承诺任意低内存状态均可启动。

48 ms 配置的调度/SD 卡抖动余量更小。主机可验证分配策略与资源释放，不能证明真机不会断音；需要录音、扬声器/蓝牙播放、暂停恢复、反复开关及阅读时播放的设备验收。

## 系统资源页面

“应用 → 系统”新增“DMA 内存”页签，显示内部 DMA 堆总量、已用、可用和最大连续空闲块。能力组合与实际 I2S 分配一致，使用同次 `heap_caps_get_info()` 获取空闲和最大块，每两秒更新，沿用低闪差分呈现。DMA 内存属于 SRAM 的重叠子集，页面明确说明不能将它与 SRAM 相加，也不能用 PSRAM 空闲替代。

## 验证与交付

`audio_dma_test.c` 编译生产 `audio_dma.inc`，注入正常、碎片化、总量不足、部分分配失败、channel 创建失败、非内存错误及启用失败；检查每次释放、RX/TX 引脚和停用次数。系统 UI 回归覆盖 DMA 页签、模拟碎片数据、条形图和不可用状态，生成实际 C 画布 `ui-system-dma-fragmented.pgm`。

全量主机测试 71/71 通过，ESP32-S31 主固件构建与 JPEG 应用链接检查通过。实际 C 页面模拟画布已检查，DMA 页签、图表及说明显示完整；`system-dma-fragmented.png` 使用模拟堆数据，不是设备截图。

验证日志、候选产物与哈希保存在 `build/audio-start-failure-20261117/`。BIN 为 7,606,800 字节，SHA-256 `664eb00c38e8945becf75937411c736277922194c7068438f3c3dccf308da79d`；ELF `396bc37dfc6d25a05adc3003c92308cde23da1a2f40a4e3390e340a989cab837`。版本保持 0.2.0。代码修改阶段仅被动采集和构建；后续授权安装见下文。未提交、未发布，没有改动 VCOM、面板时序或充电安全策略。

## 后续用户授权安装

用户明确要求“烧录”。以最近已验证安装的阅读菜单低闪候选（ELF `f2decc08a…`）为基线，重新提前布防并捕获其 45 秒启动日志，再通过新的 16 MiB 完整备份核对当前主应用、分区与原救援。原救援实际启动并完成 45 秒验证后，才写入本候选主应用。

完整 16 MiB 回读、主应用逐字节比对、引导/分区/PHY/救援/字体保护区、NVS 及启动选择器均校验通过，设置与原备份一致。最终提前布防的 45 秒采集实际观察到主槽 `0x220000`、版本 0.2.0、ELF `396bc37df…`、书库 UI ready 和 37457 ms 启动健康确认；门禁未发现错误，串口已关闭。证据在 `usb-install/result.json`、`before.bin`、`after.bin` 和各阶段日志。

以上确认安装及启动健康，不等同于实际音频验收；当前尚未在候选上记录扬声器/耳机播放、实际选用的 DMA 配置、较小缓冲的抗抖动裕量以及系统 DMA 页设备操作结果。
