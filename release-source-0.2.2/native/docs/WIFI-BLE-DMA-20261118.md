# 蓝牙页常驻 DMA 提示与 WiFi 连接下的启动预算

## 实机证据及边界

用户报告 WiFi 连接时，进入蓝牙页即常驻“DMA 内存不足，请关闭 Wi-Fi 重试”，是否点击搜索都显示。被动、不复位的串口采集见 `build/wifi-ble-dma-20261118/live.log`，结束后已关闭串口。

本次日志在 600597 ms 捕获真实一次 BLE 启动请求：DMA 总空闲 36511 字节，最大块 31732 字节，内部总空闲 67583 字节。原保护要求总空闲至少 64 KiB、最大块至少 24 KiB；此例是总空闲不达门槛，控制器未被启动。随后 600602 ms 才记录音频“播放已暂停”，证实初始化发生在释放 I2S DMA 之前。此前书籍打开阶段已有 DMA 总空闲 43051 字节，说明不能把全部不足归因于这次调用顺序。

原 UI 按 `ble.phase==ERROR` 无条件画底部消息，错误状态由工作线程一直保留，重新进入页面也会显示。它是上一次操作结果，并非页面每次绘制都在测量 WiFi/DMA。外置音频蓝牙与板载 BLE 是两个不同的工作线程；BLE 被拦截不代表耳机搜索也失败。

## 修复候选

- 新收到的 BLE 错误在列表页显示 8 秒，超时请求一次重绘后恢复设备数量/搜索状态提示。进入页面不重新展示历史错误。工作线程错误、设备记录及内存保护仍保留，不通过修改底层状态掩盖失败；BLE 详情页继续保留该设备的状态。
- 内存提示改为“低功耗 DMA 不足，音频搜索仍可用”，明确范围，去掉没有核对当前网络状态的常驻“关闭 WiFi”建议。
- 统一搜索先等待既有音频暂停/释放 I2S，再提交 BLE 请求；仍保留音频与 BLE 搜索各自的返回结果。
- 用 SDK 支持的分配策略，将启动配置 `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL` 从默认 16384 调为 1024，使应用入口之前的普通分配更早优先 PSRAM。进一步核对已安装音频候选 ELF，确认 `app_main` 已存在 `heap_caps_malloc_extmem_enable(512)`；因此应用阶段实际仍使用既有的 512 字节阈值，不能把这次配置修改说成运行时新释放了一批内存，或声称它已解决 WiFi/BLE 同时使用。显式 INTERNAL/DMA 分配、内部任务栈、64 KiB 内部保留池与显示供数要求不变。

没有下调或删除 BLE 启动预算保护，没有更改控制器内存能力要求，没有自动断开 WiFi，没有把 DMA 缓冲或任务栈迁到 PSRAM。总空闲低于保护值时依然拒绝控制器初始化，以保留对已捕获 SDK 断言重启的防护。新分配策略能释放多少内部内存、WiFi/BLE/音频能否同时运行，须安装后的实际堆数据验证，不用主机构建结果作保证。

## 验证与交付

UI 回归覆盖带历史错误进入页面、新错误显示/到期重绘、保留 BLE 底层错误、以及音频仍播放时不得先提交 BLE 搜索。既有 BLE 服务回归继续覆盖低 DMA 总量、碎片化时拦截 SDK 初始化、失败清队列及正常重试。
