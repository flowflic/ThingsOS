# 微读加载横条纹与卡死：修复候选及重启记录

后续第二候选已被用户复现为实屏冻结；JTAG 读出正常画布，现改查并修正 CKV 重启时序。最新证据与验收边界见 [CKV 调查记录](WEREAD-CKV-RESTART-20261117.md)。本文件中的首轮主机验证不代表现场问题已解决。

## 现场证据与结论边界

用户照片显示“正在加载第 56 章”，横条纹延伸到卡片以外的整屏。照片本身不能确定是供数、扫描时序还是其他阻塞。

现有 `build/online-loading-speckle-fix-20261116/live-repro3.log` 的末尾记录章节任务 action=17/error=0、chapters=3/3，随后只有相邻页缓存构建输出，没有本次卡死的调用栈，也没有可对应的扫描错误。此次被动串口采集 20 秒无输出。不能把“下载成功”当作 UI 或显示扫描成功，也不能仅凭无串口输出断定 CPU 死锁。

代码审查发现一个确认的应用层防护缺口，另对 DMA 增加诊断和校验；二者不能当成本次卡死的直接根因证据：

1. 加载的 10 MHz 时钟及失败后完整目标重建仅覆盖 `keyboard==5`。主循环首次画卡片时 `online.painted==false`，会走普通阅读/UI 输出；加载期间状态栏也是普通输出。先前退出加载的整屏重画同样没有继承加载时钟。
2. EOF 回调只按软件次数取奇偶，不验证硬件完成的描述符，且未注册描述符错误回调。WiFi/Flash 活动延迟中断时，重复旧行或补错缓冲是待查机制，现场没有其直接证据。原有 `owner_check=false/auto_update_desc=false` 与 SDK RGB 循环缓冲策略一致，不应仅凭字段关闭就判定为缺陷；首轮尝试启用它们的候选在实机启动时失败，已撤回该策略改动。

SDK 核对使用本机 ESP-IDF v6.1 的 `esp_private/gdma.h`、`src/gdma.c`、`src/gdma_link.c` 与 ESP32-S31 AXI DMA LL；未修改 SDK 或参考仓库。

## 本次改动

- 首次完整加载、卡片变化、转圈、加载状态栏以及退出加载后的整屏清理，均经加载专用输出。整屏输出明确请求完整 GC16，区域输出保留原有区域边界；横竖屏均覆盖。
- `online.cleanup` 在取消、章节就绪或离开加载时保留到成功提交后，失败不丢弃整屏清理请求。章节缓存和阅读位置不因此删除。
- 保留 SDK 原有 DMA 循环缓冲策略。首轮启用 owner 检查与 TX writeback 的候选未通过实机启动门禁，因此后续候选撤回这项未经硬件验证的策略改动。
- EOF 必须匹配预期的硬件描述符；错序、无效事件或描述符错误立即终止当前扫描并锁存故障。即便软件已准备全部行，完成回调仍将 DMA 故障转成 `0x400`，交给已有安全时钟、完整画布重建和清屏恢复路径。正常最后一块结束后不再重交 descriptor owner。
- 沿用工作区已有的 1500 ms DU 转圈、64 字节描述符隔离/同步、触摸与按键等修改。未更改版本、VCOM EEPROM、充电策略或面板行时序，未提交、未发布、未刷写。

DMA 校验可能把过去未上报的供数问题转成可见的恢复清屏；其发生频率和恢复效果需要真机验证，主机回调测试不模拟 DMA 预取或硬件描述符写回，也不证明中断延迟裕量。
