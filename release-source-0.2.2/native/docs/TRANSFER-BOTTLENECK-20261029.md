## 已确认原因

1. SD实际写入及最终同步合计仅1.851秒，不是本次五分钟上传的主要耗时。
2. `main.c` 的上传忙碌分支每约两秒检查 `transfer.serial`，持有
   `thingsos_io_lock` 调用 `transfer_draw()` 与 `thingsos_board_present()`。
   `management.inc` 在传输页直接调用完整 `draw()`，即整页绘制。
   网络上传每次写入也必须等待同一把锁，日志确认累计等待141.338秒。
3. `network.c:transfer_set()` 每次接收后都递增serial，即使百分比未变。
   因而同一百分比也可能触发重复整页更新。
4. 主循环普通路径已有每10%更新进度的限制，但上传忙碌路径在此之前
   `continue`，绕过了该限制。这是与现场频繁刷新一致的具体代码缺口。

## 接收等待的证据边界

接收调用里的149.987秒不能全部等同于无线空口慢。
上传线程等待显示锁时无法继续消费后续数据，可能对TCP发送方形成背压。
当前TCP接收窗口5,760字节、MSS 1,440字节，STA使用11b/g兼容协议。
这些是当前代码和配置事实；本轮没有抓包，尚不能分离背压、延迟确认、
重传、手机调度或无线链路各自造成的时间，也不能声称修改窗口或协议已证明有效。

## 优化顺序

首先修正忙碌路径的刷新条件，按用户后续决定，普通文件上传按进度跨越20%或状态改变才更新，
开始、完成和错误仍及时显示，避免同一百分比重复整页重画。
保留I/O互斥及OTA与显示的安全边界，不通过取消锁实现并行。
用相同手机、路由器和文件再次测量阶段耗时，确认等锁下降及整体吞吐变化。
若接收等待仍高，再针对TCP接收窗口、消费方式和Wi-Fi协议做分别的对照实验。
原测速轮次只做测量与定位；不能由该结果承诺具体提速倍数。

## 后续20%刷新修正

用户确认改为20%一次。忙碌路径在获取I/O锁之前，先判断进度是否跨越
20%档位，避免同一档位因serial变化或两秒经过而重复绘制。
普通主循环的非OTA上传进度也使用同一判断，防止退回原10%路径。
初次状态、文件名/阶段变化、进度重置、完成、中断及错误独立触发更新。
OTA的进度刷新频率保留原先逻辑，I/O互斥、网络参数及波形不变。

状态快照存入原有PSRAM应用状态中。
主机回归用0到100的每个百分比、每百分比五次serial变化进行测试，
开始后恰好在20/40/60/80/100触发五次进度更新；
