# 微读离线阅读时长补传

2026-11-13，Metalio 0.1.7 开发候选。版本号保持不变；离线补传功能尚未通过真实账号实机验收；USB 安装和基本启动健康已验证，见后文安装记录。

## 使用方式

微读 → 同步 → 离线阅读时长补传：

1. 先登录微读，点击“离线阅读时长补传”开关。已有同账号 E-Ink 授权时直接复用；缺少授权或已失效时自动进入扫码，需用同一微信读书账号确认。Web 登录不能直接代替首次 E-Ink 授权。
2. 扫码成功后才保存为开启；取消、失败、断网或设置保存失败均不会把原本关闭的开关变为开启。同时保留“上报阅读时长”和已有用户同意选项。
3. 再次打开微读书籍后，本次阅读的在线和离线时长统一进入本地账本。普通本地 EPUB/TXT、内置示例和公众号不进入该通道。
4. 重新联网且界面空闲时自动补传。正常页面仅保留一个操作开关和只读状态；出现授权失效、云端位置冲突或待确认时长时，才显示对应入口。原有进度上传设置独立生效，补时长不携带章节位置。

该选项默认关闭。不追溯上传启用前的设备总统计。阅读中修改时长通道在下次开书时应用；关闭会立即停止新采集并暂停自动补传，保留既有队列。E-Ink 授权过期后保留待发片段，重新授权后继续，不将其转成 Web 时长重报。取消/退出微读授权不会删除其他账号目录中的队列。

正常页面不再提供常驻的“授权时长通道”和“立即补传”按钮。已开启通道的重新授权失败不会改动原设置或清空账本；位置冲突需用户在微信读书核对后点击确认，再由自动流程继续，仍遵守冷却时间。“待确认时长说明”仅展示原因与核对方式，不重传、删除或自行确认这些记录。具体修改与验证见 [单开关交互记录](WEREAD-READTIME-SINGLE-TOGGLE.md)。

## 实现与恢复

- 通过 runtime 接收已通过阅读页、遮罩、闲置边界和调度空档检查的有效区间，在主任务内写入 PSRAM 缓冲；回调不做网络或磁盘 IO。
- 以 `gettimeofday` 的墙钟归属历史小时，单调时钟决定有效毫秒数。当前设备使用既有固定 CST-8 时区，上传原始 `+08:00`。本功能没有新增修改时区的选项。
- 约每 30 秒及正常关书/休眠边界落盘；网络任务期间先保留 RAM 缓冲，任务释放后再检查点。意外掉电可能丢失最后一次尚未落盘的缓冲，不能承诺零丢失。缓冲为 32 个窗口，满时明确停止采集并提示，不覆盖未发的完整秒数。历史整点残留不足一秒的余量可在窗口满时退休，协议精度为整秒。
- SD 目录为 `/sdcard/.thingsos/weidu/readtime-<账号MD5>/`。每片段固定 128 字节，显式小端编码、格式标记和 CRC；含 bookId、小时、真实采集结束时间、秒数、版本和异常标记。每账号最多 8192 个待处理文件，满后暂停保存并提示。临时 `.tmp` 不作为已提交记录恢复。
- 独立 E-Ink 凭据保存在设备 NVS，不改变 Web vid/skey/rt 结构。按账号保存已落盘采集的墙钟水位；发生回拨时暂停采集，未来片段等待时间恢复。未知时间不会伪造成重新联网当天的阅读。
- 新代码尚未从既有下载缓存中取得可信 E-Ink 书籍版本，使用协议兼容值 `bookVersion=0` 表示未知，不拿云端最新版本冒充本地文件版本。批次接口保留版本隔离能力，后续可独立补齐下载元数据。
- 单批最多 512 个片段、12 个小时/时区组、24 小时以内跨度，按同书、同版本聚合。超过单批资源上限的余量继续待发，不使用早期 600 秒/100 条限制。
- 本地冷却、授权/配置检查和 TCP/TLS 建连都在认领之前。紧靠首个 POST 正文字节之前，先将认领记录写入 `.sent` 并 flush、验证，再移除 `.pending`。掉电后两者同时存在时 `.sent` 优先，不回放。
- 请求可能已发送而无明确成功回执时保持 `.sent`，页面显示为“待确认”。超时、401、429、HTTP 200 但 `succ` 不为 true/1，均不能据此自动重报。明确业务成功后只清理本批认领的记录；清理失败留下的记录仍不会自动重传。
- 单批检测到某小时超过 3600 秒时，超量来源改为 `.held` 隔离并保留，正常记录继续处理。它与已发送但结果未知的 `.sent` 分开统计。该检测不是服务器跨设备去重保证。
- 自动和手动操作均遵守持久化冷却。成功后至少等待 10 秒，普通失败等待 60 秒，429 等限频等待 30 分钟。授权恢复不清空旧队列。
- 成功确认先落盘，再核对云端位置；位置变化或核对失败会暂停后续补传，用户核对后可继续。它不撤销已确认的时长，也不重新发送待确认批次。

这里采用单写者模型：网络 worker 活跃时，主任务只采集 RAM，不读写账本；worker 完成后才能由主任务做检查点。网络 worker 进行网络和账本扫描时不占用显示锁；主任务检查点沿用主任务的显示互斥，NVS 凭据写入保留短时显示互斥。后台不会直接操作屏幕。
